# ADR-0002：电子签名法律效力与合成方案选择

**日期**: 2026-08-11  
**状态**: 已采纳  
**相关需求**: OW-704 Document Signing

---

## 背景

OW-704 的签署功能需要选择 PDF 合成方案：

- **后端合成**（PDFsharp）：服务端完全掌控合成过程，审计链完整，但需要处理 Dockerfile 字体问题
- **前端合成**（pdf-lib）：浏览器直接生成 PDF，省掉后端 PDF 库，但后端只收到文件无法验证内容

决定因素是业务场景的法律效力要求。

## 与 BA 确认结果

**法律效力要求不高**，签署场景（合同签署、交付验收、审批签字）主要用于内部流转确认，不需要具备上法庭举证能力的可靠电子签名。

## 决定

**采用前端合成方案（pdf-lib）**，后端负责接收文件、计算哈希、存储、记录审计元数据。

具体架构：

```
前端（浏览器）                          后端
─────────────────────────────────────────────────────
1. PDF.js 渲染 PDF 预览
2. 用户拖拽放置签名/日期
3. pdf-lib 将签名/日期合成进 PDF
4. 生成 ArrayBuffer
5. POST 已合成的 PDF 文件 + 签署元数据
                                ──────────────────────>
                                6. 后端接收文件
                                7. 后端自己计算 SHA-256 哈希
                                8. 存储哈希到数据库
                                9. 上传文件到 Blob Store
                                10. 写签署记录（签署人、时间、
                                    source_file_id、file_hash）
```

## 哈希存储的目的

- **当前用途**：系统内部防止已签署文件被替换——如果文件被修改，SHA-256 哈希与数据库存储值不一致，可检测出篡改
- **未来用途**：为用户真伪判别功能留基础——用户上传一个 PDF，系统计算其哈希与数据库比对，判断是否为系统生成的已签署文件

> 关键点：哈希必须由**后端收到文件后自行计算**，不能信任前端传来的哈希值（前端可以伪造）。

## 为什么不用前端计算哈希

前端合成后计算哈希并上传，后端无法验证「这个哈希是不是真的对应这个文件」。用户可以上传任意 PDF + 任意哈希，系统无法识别。因此哈希必须后端自己算。

## 影响

- **省掉**：PDFsharp NuGet 包、Dockerfile 字体处理
- **新增**：前端 `pdf-lib` 依赖（`pnpm add pdf-lib`）
- **后端 API 变化**：从「接收坐标+签名图片」改为「接收已合成的 PDF 文件 + 元数据」
- **数据库**：签署记录表需要 `file_hash`（SHA-256，varchar(64)）字段

## 后续增强路线图（本期不做）

如果未来业务需要更高法律效力，可以在此基础上叠加：

1. 签署时短信/密码二次验证（Intent to Sign）
2. PDF PKI 数字签名（需引入 iText7 商业版或第三方签章服务）
3. 审计记录补充 IP 地址、User-Agent
4. 文件长期存储策略（保留期限、冗余备份）
